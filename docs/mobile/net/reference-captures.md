# Reference Captures & Protocol Diffing

Real-game captures of the mobile client, for diffing the mobile protocol against desktop and against
Project X's output. Captures live under **`data/client/android/captures/`** (gitignored — local only), produced
by `mobile/rs3-capture.py`.

## The login/world capture — `mobile-official-lobby-world-login/`

A full **real-game** init → lobby-login → world-login → in-game session captured against live Jagex servers
(so the protocol is correct and complete — Project X's mobile login is still incomplete). `[VERIFIED — artifact]`

| File | What it is |
|---|---|
| `packets.jsonl` | One JSON object per event — the machine-readable index. Fields: `t` (seconds), `dir` (`s2c`/`c2s`), `op`, `size`, `src` (`decoded`=via TcpIn, `opcode-only`=outgoing opcode), `hex` (full payload). ISAAC records: `{kind:"isaac", which, keys}`. |
| `packets.log` | Human-readable, full untruncated hex per event (75 MB). `[CONN]`/`[DISC]`, `[ISAAC]`, `[S->C]`/`[C->S]` op lines, `[stream]` login bytes. |
| `stream-c2s.bin` | Raw client→server bytes on the game socket (login handshake included) — the RSA login block etc. |
| `stream-s2c.bin` | Raw server→client bytes (login response, JS5 master-index, world data). |

### Timeline anchors (this capture)
- `t≈2.5` — first ISAAC pair (`c2s-raw` + `s2c`+50): the **JS5** connection (type `0f`=15) sets up its cipher.
- `t≈2.6` — `[C->S] len=44 0f2a000003b5…<32-char token>` — JS5 init carrying a session token; server serves the master index (`43…`, ~5.8 KB).
- `t≈100.0` — `[C->S] len=1 0e` (type 14 = CONNECT_LOGIN), then `t≈100.88` `[C->S] len=706 1302bf000003b5000000010081…` — the **lobby login**: opcode `13`=19 (LOBBY), varShort 703, build `949.1`, then the RSA block.
- `t≈102+` — decoded `[S->C] op=…` game packets (op 4, 78/UPDATE_ZONE, 20, 95) — post-world-login, in-game.

### Reading it

```bash
# high-level flow (connections, ISAAC, login) without the huge payloads:
grep -E '\[CONN\]|\[DISC\]|\[ISAAC\]|len=706|len=44' packets.log | head

# the lobby login packet, full:
grep 'len=706' packets.log | sed -E 's/.*len=706 //'

# structured filter (needs jq or python):
python3 -c "import json; [print(r) for r in map(json.loads, open('packets.jsonl')) if r.get('op')==78][:5]"
```

## Diffing against Project X / desktop

The point of these captures is to find where Project X's mobile behavior must differ from desktop:

1. **Login block layout** — compare the real `len=706` opcode-19 block (build, RSA size, field order) against
   what `lobby/.../LobbyLoginHandler.kt` parses. The mobile *username+password* (directlogin) block layout is
   documented in [login-handshake.md](login-handshake.md); the capture shows the OAuth default, so diff both.
2. **Post-login interface/var/script setup** — the decoded `op=…` S→C packets after login are where the
   client is told which interface tops/subs to open and which varps/varbits to set. Mobile differs from
   desktop here (see below). Decode opcodes via the desktop `ServerProt` names + Project X's `register949`, then
   map the interface/var ids with the shared tooling:
   - `re-resources/gamevals/gameval.py component <id>` / `interface <id>` / `var_player <id>` / `varbit <id>`
     — id ↔ dev-name.
   - `cs2-dump/` (generated by `:tools:cs2 decompile-all`) — grep for the interface/var to see what the clientscripts do with it.
3. **Byte transforms** — match read/write shapes against `re-resources/docs/net/buffer-transform-patterns.md`.

To capture Project X's side for a direct diff, run a private-mode capture (`mobile/rs3-capture.py --gadget
--host <projectx>`) and diff its `packets.jsonl` against this one, aligned on opcode sequence.

## RESOLVED: how does the lobby know the client is mobile?

`` `` `[VERIFIED — artifact, XTEA-decrypted capture]`
The mobile op19 (lobby) / op16 (world) login descriptor — the XTEA-enciphered tail — carries the OS in
**three** fields; the login-details **response** carries **no** OS field. Full analysis and byte-map in
[login-handshake.md §6](login-handshake.md#6-mobile-detection-signal--how-the-server-tells-a-mobile-login-from-desktop--task-3b).

Signals, ranked:

1. **`"NXT-Android"` client-name string** — embedded in the machine-info block at XTEA-tail **off ~269 in
   both lobby and world** (desktop sends `"NXT-Windows"`/`"NXT-Linux"`/`"NXT-Mac"`). **Recommended**: it
   holds a near-constant position across both branches, so `LobbyLoginHandler`/`WorldLoginHandler` can
   detect mobile by scanning the decrypted tail for this literal.
2. **`binaryType` byte = `0x07`** — the client's own mobile self-test (`binaryType ∈ {7,8}`). Protocol-
   clean single byte, but at **different offsets** in lobby (off 377) vs world (off 358).
3. **`platformType` byte = `0x02`** — `jag::GetPlatformType` enum, immediately after `binaryType`.

The earlier candidate "correlate the `binaryType=7` config fetch" is unnecessary: the flag is **in the
login block itself**. The connection-type bytes (`0f`/`0e`) do **not** distinguish mobile.

**Server action:** read one of the three from the C2S login descriptor to mark the session mobile, then
serve the mobile interface/var/script set post-login. Do **not** add an OS byte to the login-details
response — the client's decoder consumes a fixed field list and would desync. Tracked (resolved) in
[../OPEN-QUESTIONS.md](../OPEN-QUESTIONS.md).
